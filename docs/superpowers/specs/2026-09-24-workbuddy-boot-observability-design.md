# WorkBuddy 背景启动与日志可观测性设计

## 目标与范围

修复 WorkBuddy 初始无背景媒体时默认壁纸无法铺设的问题，并让 Windows 原图标启动链路的守护日志可用、有限增长。对报告中的中文主题名乱码只增加不泄露名称的边界诊断，定位后再决定修复，不凭旧状态文件执行猜测性转码。本设计不更改 WorkBuddy 原图标、CDP 修复窗口、已保存主题格式、用户背景文件或 Cursor/豆包行为。

## 已确认的故障边界

页面运行时的 `stageEl()` 目前按需创建舞台；runner 在应用默认壁纸时遇到舞台不存在会返回 `no-stage`。首次无已保存主题的页面可以走到这一分支。Windows 手动 `install` 的 `startDaemon()` 打开日志文件并把 PowerShell 的标准输出/错误指向它，但登录 VBS 启动链路不拥有这一重定向；外部测试显示直启 Node 有日志而经 PowerShell 启动的日志可能为 0 字节。具体是 PowerShell 转发还是启动前失败，需要用相同运行时和同一日志路径的受控测试区分。

## 舞台与状态设计

背景 UI 完成挂载时即确保舞台存在，继续复用现有 `stageEl()` 的幂等创建与重挂检测，不在 runner 中复制 DOM 创建逻辑。runner 对初始无媒体且未显式清除的状态铺默认壁纸；随后恢复持久化主题时替换默认媒体。`cleared=true` 始终优先于默认壁纸，重新连接、页面重载或重挂也不得把用户清除的背景重新铺回。重复注入只保留一座舞台、一份媒体和一条入口；失败不清除原有主题状态。

## 日志与诊断设计

runner 的关键生命周期日志由自身写入 `%LOCALAPPDATA%\beautiCode\logs\wb-runner.log`，不依赖 PowerShell 是否转发标准流。文件按大小有界轮转；写日志失败不得让守护崩溃，前台运行时应向标准错误报告。`wb-setup status` 只读报告日志文件是否存在、是否可写及最后更新时间；空文件不能单独证明守护停止。launcher 负责把“Node 尚未启动前”的指针、路径与版本错误写入同一日志中的安全错误码，不记录完整命令行、媒体路径或账号信息。终端交互执行仍保留必要的标准错误反馈。

中文名称诊断只在皮肤中心应用流程采样：比较目录解析后的名称、传给页面的名称以及落盘前后名称的 UTF-8 哈希与长度，记录阶段和是否相等，不记录原文。测试使用固定的中文样例验证 JSON/页面/状态链路；若真实目录一进入本进程便已乱码，先定位上游响应或解码环节，本轮不修改旧主题名称，也不自动重命名用户主题。

## 验证与回滚

自动化测试覆盖无状态首次启动、已有图片/视频、`cleared=true`、页面重挂和重复注入；Windows 测试分别从手动安装与登录 VBS 链路启动守护，确认启动、连接、失败三个阶段均可读到有界日志，并确认日志未泄漏路径/名称。主题名测试证明“室内”等非 ASCII 名称在本地链路不被二次损坏；实际旧状态乱码仍标为待定位，不能宣称修复。对约 800 MB 视频和已保存主题做回归验收，确保新增舞台/日志不改变媒体加载与恢复。

相关源码：`packages/adapter-workbuddy/src/background-bar.ts`、`scripts/{wb-cdp-runner.mjs,wb-setup.mjs,portable-runtime.mjs}` 与相应测试。优先拆出独立日志职责，不继续扩大已超 500 行的 runner 文件；DOM 修复保持最小边界变更。若回滚本补丁，已有状态与媒体文件保持不变。
