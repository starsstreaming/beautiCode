# 五端背景设置与动态场景统一设计

状态：用户已确认，实施中。范围是 Cursor、WorkBuddy、普通豆包、Codex 和豆包工作；DSH 是参考实现。目标平台先覆盖 Windows，同时保留已有的 Linux 能力。

## 目标与现状

五端在各自原生设置中提供一致的背景能力：功能面板不透明、背景阴影、背景磨砂、声音、导入背景、已保存背景、皮肤中心、Wallpaper Engine 本地壁纸库和清除。导入时先命名，默认使用文件名或壁纸项目标题。图片、视频和兼容的 Wallpaper Engine Scene 均能应用、保存、切换和恢复；Scene 必须真实动态渲染，海报不算成功。

各宿主守护程序应在用户登录后隐藏启动；用户退出客户端时保持等待，之后重新打开客户端可重新注入。不同宿主的启动限制不同，不能为代码相似而使用同一套关闭或重启策略。豆包工作保持现有「设置 → 外观设置」挂载位置。

当前豆包工作已有九项设置、视频播放和重启后自动注入；其 Scene 仍是预览图。Cursor、普通豆包、WorkBuddy 和 Codex 当前工作树仍使用各自的侧栏入口。另一个未提交工作区 `codex/dsh-wallpaper-scenes` 已有 DSH Scene 原型、壁纸库服务和 Codex 设置页实现，但其基线早于当前 Linux 支持；不能直接覆盖当前工作树或整体合并未提交文件。

## 方案

推荐复用 DSH 原型中的场景项目校验、受控资源服务、WebWallGL 渲染器和首帧回执，将宿主无关能力放进共享模块；每个适配器只负责识别自己的设置页面、调用桥接接口和确认真实渲染。DSH 原型中的 Codex 设置页可作为迁移依据，需逐项对照当前分支后重新验证。

备选方案是让每个宿主各自实现一套场景播放器，或嵌入正在运行的 Wallpaper Engine 原生窗口。前者会重复安全、事务和故障处理；后者引入额外运行依赖与宿主窗口耦合，也无法复用 DSH 的现有数据流。两者都不符合本次统一目标。

## 模块边界与数据流

1. **宿主设置适配器**：只识别已测量的原生设置容器，挂载符合宿主语言、浅深色和可访问性要求的背景视图；结构不匹配时不注入到猜测的位置。
2. **宿主桥接层**：将视图操作转换为受限命令和能力标识；不把用户本地绝对路径、目录授权或控制令牌交给页面或不可信场景。每端提供自己的状态查询、取消和结果回执。现有豆包工作页面可直接提交路径的接口必须删除，由守护进程持有路径并签发短期 ID。
3. **共享背景领域能力**：统一项目类型、文件校验、库索引、主题命名与场景资源生命周期；在边界转换现有宿主状态，不让 DOM、CDP 或持久化细节进入领域模型。只为五个真实宿主共同使用的能力建立接口。
4. **场景运行时**：复用固定版本 `webwallgl@3.0.0` 的现有构建与兼容性修补。可信宿主取得受限的本地包后，将包字节和经过校验的项目数据交给不透明源的沙箱 iframe；场景不获得宿主 DOM、目录能力或控制令牌。
5. **应用事务**：先准备候选背景，收到真实首帧后才替换旧背景并保存状态；取消、超时、解码失败、上下文丢失或宿主不支持时释放资源并保留上一背景。海报仅用于列表预览，不能冒充场景首帧。

数据流为：设置视图 → 宿主桥接 → 共享校验与暂存 → 场景渲染 → 首帧回执 → 提交主题。图片和视频继续走各宿主已经验证的媒体管线；不要为外形相似而统一其不兼容的宿主实现。

### 选择与应用契约

- 手动导入 Scene 使用原生文件选择器选择 `project.json`；其他 JSON、Web/Application 壁纸及无效项目在准备阶段拒绝。图片和视频继续使用现有格式选择器。库中选择和手动选择都预填项目标题或文件名，允许用户修改名称。
- 守护进程保存真实路径，并向视图返回绑定宿主、当前连接和操作代际的随机选择 ID、显示名称及类型；选择 ID 最长有效 10 分钟，断开、取消或会话更换时撤销。应用请求只携带该 ID、名称和操作代际。
- 每个宿主只有一个活动写入者；准备、首帧、提交和取消均带代际。较早请求的迟到回执不得覆盖新背景；提交状态与主题清单使用原子替换。设置页关闭只是视图关闭，不应被健康检查当作入口损坏。
- 运行中的切换失败保留当前画面。冷启动恢复时若源文件已消失，保留已保存主题记录并显示原生背景与错误，不承诺保留不存在的旧画面。

### 场景资源桥接

DSH 原型的播放器从 `/__beauticode/scene-frame.js` 读取 bundle，资源服务默认信任的来源也不是其他桌面宿主。各适配器必须提供经过校验的当前会话来源和本机资源桥：可信父页面只通过带短期令牌的回环地址读取 bundle 与 PKG，之后经一次性 MessageChannel 把字节传入不透明源 iframe；不把 URL、令牌或本地路径传给 iframe。豆包工作实机页面的来源是 `chrome://doubaowork-chat`，不能把其 CDP target 的 `doubaowork://` 地址当作 Origin。

每端先验证实际 Origin 和 CSP，只允许精确匹配的可信来源；不使用 `*` 或 `null` 放行。宿主阻止可信父页面取得资源或不允许安全沙箱时，终止场景应用并报告原因，不修改宿主 CSP。

## 宿主接入

| 宿主 | 当前依据 | 接入与验证要求 |
| --- | --- | --- |
| 豆包工作 | 已在外观设置挂载；独立 CDP 适配和状态文件 | 保持入口位置与现有视频播放；验证宿主 CSP 是否允许隔离场景播放器，原有 Scene 主题从项目路径重新尝试动态加载 |
| 普通豆包 | 当前使用侧栏入口和共享桌面 CDP 运行时 | 实测原生设置结构后迁入设置；不能沿用豆包工作的选择器猜测其页面 |
| Cursor | 当前使用侧栏入口和共享桌面 CDP 运行时 | 实测设置页和目标窗口；保留现有 Windows/Linux 目标识别及启动策略 |
| Codex | 当前分支使用侧栏面板；另一工作区已有设置页原型 | 对照现有 Linux 修复后迁移设置模块；再独立接入场景事务和真实宿主回执 |
| WorkBuddy | 当前侧栏面板与独立守护实现 | 实测设置页、背景层和重挂载；保留现有宿主生命周期与平台支持 |

每端的目标页、锚点、设置挂载点、媒体来源策略和沙箱限制必须以该版本的实际宿主证据确认。若宿主 CSP（内容安全策略）阻止隔离场景运行，显示可诊断的失败并保留旧背景；不得关闭沙箱或放宽宿主策略来强行通过。

## 状态、兼容与安全

- 保持现有系统用户及宿主数据隔离。已保存的主题名称、ID、图片/视频路径和当前偏好不得因迁移丢失；如果必须更改持久化格式，先校验并生成可回滚备份，再一次性迁移，不长期双写。
- 现有豆包工作 Scene 记录指向 `project.json`。迁移保留记录和名称；恢复或切换时尝试真实场景加载，失败明确提示并保留原背景，不把预览图报告为动态播放成功。
- 用户打开本地壁纸库时，五端自动发现并扫描当前用户 Steam 配置指向的标准 `workshop/content/431960` 目录，延续豆包工作无需手选目录的行为；非标准目录必须由用户明确选择。根目录与主题绑定按宿主保存，不能把一个宿主的主题 ID 当作另一宿主的绑定。
- DSH 默认使用 `hosts/dsh/wallpaper-library.json`，豆包工作当前使用根目录下的同名文件。豆包工作迁移时只复制并重新校验已有根目录，主题以该宿主自己的状态为准；保留原文件供回滚。若用户自定义数据根导致文件实际重合，先检测真实路径并拒绝并发覆盖。库写入使用锁和原子替换；损坏的现有文件应报告错误，不得静默改写为空配置。
- 壁纸库只访问经校验的本地根目录。目录穿越、UNC/设备路径、符号链接、文件替换与非法项目都必须拒绝或隔离为单项错误；来源文件只读，不随清除或删除主题而删除。
- 场景包默认静音；声音开关、页面不可见时暂停、恢复、尺寸变化和销毁均通过受限消息协议处理。限制项目元数据、包大小、并发读取和资源生命周期；错误日志不包含令牌、账号或完整路径。
- DSH 原型的 iframe 并非独立进程，不能保证阻止恶意场景的全部资源耗尽或自导航。动态内容只能在不暴露宿主能力的沙箱中运行，并设置心跳、超时及可终止的宿主边界；无法限制脚本导航或恢复失控渲染时，对需要该能力的项目安全失败，不能通过放宽隔离实现兼容。禁止声称 iframe 提供完整恶意代码隔离。
- 维持 DSH 已确认的高画质策略，不静默降画质。场景包上限 512 MiB；同一系统用户同时最多暂存一个场景，等待应有界且可取消。已运行的多个宿主可各自播放，但内存或 GPU 资源不足时必须报告失败并释放候选资源。打包携带 WebWallGL 及其依赖的许可说明；离线运行不等于全新环境可在无依赖缓存时断网构建。
- 仅支持渲染器实际兼容的 Scene 项目；不承诺与 Wallpaper Engine 原生引擎的所有特效等价，也不扩展到 Web/Application 壁纸。

## 实施顺序与验收

1. 对照两个未提交工作区，提取并验证共享 Scene、壁纸库和构建产物；保留各自原始工作区及现有 Linux 变更。先完成隔离渲染、首帧失败回滚和主题数据兼容测试。
2. 以豆包工作为首个桌面宿主，验证真实动态 Scene、图片/视频/场景互切、重启恢复、声音及清除；保留现有自动注入策略。
3. 迁移 Codex 设置入口并接入场景，再分别接入普通豆包、Cursor 和 WorkBuddy；每端先测量设置 DOM，再实现并验收，不能从另一个宿主推定兼容。
4. 为每端验证加载、空状态、错误与重试、键盘操作、浅深色可读性、窗口关闭后重开、守护重启和资源释放。动态场景验收除首帧外，还需证明画面随时间变化且实际透过宿主内容可见，并检查声音、隐藏暂停与恢复。测试必须区分合成浏览器夹具、真实客户端及硬件负载证据。
5. 打包后检查依赖、运行时模块与离线构建，运行构建、类型检查和相关测试；迁移会修改的超 500 行文件应按职责拆分。未完成真实宿主验收的能力不得标记为已验证。
